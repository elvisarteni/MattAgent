Vero Availability Monitor 3: setup and user guide

A small local tool that answers one question all day long: is Vero available right now? It checks Vero on a timer and shows the answer, with its history, on a status page.

Version3.0.0 (replaces the 0.x latency monitor)
StoryASPF-1578: As a Quality Lead, I want to monitor latency in the VERO CLI responses. Refocused on availability (ADR-002).
Owner<< OWNER >> (Quality AI Automation, GenAI Group 3)
Based onSCMP v0.5 (ASPF-1619) and Vero Chat and Vero CLI: integration guide, draft 0.1 (measured behaviour of Vero CLI 2.3.3 and WChat MCP Server 4.0.3)
Runs onWindows 10/11 laptop (also Linux and macOS), Python 3.8+, no admin rights, nothing to pip-install

1Overview

Vero Chat chat (optional)MCP initialize handshake with verostudio.sw.nxp.com/mcpThe Vero Chat endpoint is up and accepts your tokenfree, no model call
Acceptance criterionHow V3 meets it
Should execute the cheapest promptOne fixed, harmless prompt on a pinned cheap model (Haiku 4.5 by default), plus two checks that cost nothing.
Should support time trigger setupsetup.bat installs a Windows Task Scheduler task that runs on battery and catches up after sleep, or a cron entry on Linux/macOS. The status page can also run the timer itself.
Record and dashboard dataEvery run goes into SQLite and gets a JSON run manifest. The live status page shows the current status, availability for 24 h, 7 d and 30 d, a timeline and incidents. You can export CSV or a snapshot.
Should be automatedAfter setup nothing needs a person: scheduled checks, the status page starts at logon, old data is pruned and logs rotate.

2How it decides

Checkavailabledegradedunavailable
cliexit code 0–not found, exit code ≠ 0, or 30 s timeout
taska completion_result event arrivesslower than 90 s, or the answer does not contain "OK" (for example a guardrail refusal)no completion_result, an error exit, or the 210 s hard limit (the process tree is killed)
chatthe MCP initialize result arrivesit takes longer than 10 stoken variable missing, HTTP 401/403, unreachable, an MCP error, or a reply that is not MCP

Overall status of a run:

  • unavailable if the main check is down. The main check is the task when it is enabled, otherwise the CLI.
  • degraded if any other check is down, or any check is degraded.
  • available otherwise.

Availability is the share of runs that were not unavailable. An incident is a stretch of consecutive runs that were not fully available. It counts only if it includes an outage, or if the degradation lasts at least 2 runs, so a single slow answer does not flood the list (it still shows on the timeline). An incident ends at the next available run.

The task check follows the measured Vero CLI contract (integration guide §3.3):
  • the answer is only the completion_result event, and partial fragments are ignored;
  • the real provider and model are taken from modelInfo and written to the run manifest;
  • api_req_started, which contains the full upstream prompt, is never stored or logged.

4Requirements

  • Python 3.8 or newer. Install it from Software Center, from python.org (tick Add python.exe to PATH), or with winget install Python.Python.3.12.
  • Vero CLI installed (npm, so it resolves to vero.cmd) and authenticated (vero auth) for the Windows user who will run the monitor.
  • Optional, for the Vero Chat check: a Vero Chat token in a user environment variable (section 6).
  • No admin rights. The status page listens on 127.0.0.1:8766 only. Data is about 2 MB for 90 days.

5Install

  1. Get the folder into C:\Tools\vero-availability-monitor. Use a local folder, not Downloads or OneDrive. There are two ways:
    • Git (recommended): clone it from Bitbucket project QAI << repo URL >>.
    • Rebuild document: give VeroAvailabilityMonitor_3.0.0_REBUILD.md to Vero CLI or another AI assistant with: "Follow the instructions at the top of this file and rebuild the project in C:\Tools". The assistant writes every file, checks each one against its SHA-256 and runs the tests. Then copy this guide into docs\.
  2. Optional demo: double-click setup_demo.bat. It uses a fake Vero CLI and seven days of sample data, kept in data-demo\.
  3. Double-click setup.bat. It asks seven questions; Enter keeps each default. Then it runs doctor, one real check that stores nothing (the task part takes about a minute), and asks Install background monitoring? [Y/N].
  4. Y installs the scheduled check and the status page at logon, puts a Vero Status shortcut on the desktop, and opens the page. Check everything any time with status.bat.

1. Vero CLI program (name or full path; `where vero` shows it) [vero]:
   found: C:\Users\me\AppData\Roaming\npm\vero.cmd
2. Model id to pin (-m), cheapest first [us.anthropic.claude-haiku-4-5-20251001-v1:0]:
3. End-to-end task check (~1 min, 2 small model calls per run) (y/n) [y]:
4. Also check Vero Chat (MCP handshake, free; needs a token variable) (y/n) [n]:
5. Check every N minutes [15]:
6. Task timeout, seconds [180]:
7. Task counts as slow (degraded) above, seconds [90]:
  • Model: pin the cheapest model your Vero allows. The run manifest still records the model Vero actually used, which a stored task or a configuration change could override.
  • Task arguments: the default is task --json -m {model} -t {timeout} -c {workdir} {prompt}, in vero.task_args. --json is required. {workdir} is the empty folder data\sandbox.
  • No --yolo (ADR-003). The probe only needs the agent to complete, not to touch files or run commands.
  • Timing: the defaults are based on the measured figures (p50 52.7 s, p95 59.2 s). Interval and timeout are validated together, so a run can never be longer than the interval.

Vero Chat token (only if the chat check is enabled)

The token is never written to the config. The check reads it at run time from the environment variable named in chat.token_env (default VERO_CHAT_TOKEN). Set it once for your user, then sign out and in again:

setx VERO_CHAT_TOKEN "<token from Vero Studio>"
A user environment variable is readable by programs running as you. Follow your security policy. For permanent monitoring, use a functional-account token and record it in functional-accounts.md, as the SCMP and guide §9 decision 5 require.

12Security

  • No auto-approval: never --yolo, an empty working folder, a fixed harmless prompt (ADR-003).
  • No content kept: the event stream is parsed in memory. The full upstream prompt (api_req_started) and the model answer are never stored. A test proves it with a decoy secret.
  • No secrets stored: the Vero Chat token comes from an environment variable at run time. Error details are cut to 200 characters, and anything that looks like a credential (bearer, token=, password=, aws_secret) is masked.
  • Local only: the page binds to 127.0.0.1. Requests for other host names are rejected (no DNS rebinding), and so is "Check now" from other websites (Origin check).
  • Known Vero facts (guide §3.7): Vero itself keeps task history in %USERPROFILE%\.vero\data\tasks, and MCP bearer tokens in clear text in vero_mcp_settings.json. The monitor's tasks add small entries there; clean them up according to your policy.

13Troubleshooting

Start with status.bat, then data\monitor.log, then python vam.py doctor.

Reason shownFix
cli: 'vero' not found on PATHGive the full path in configure (where vero); scheduled tasks may have a different PATH.
task: exit 1: … UnauthorizedRun vero auth as the same Windows user the task runs as.
task: no completion within 210 sVero hung, or waited for an approval. Run the task command by hand (doctor prints it as task cmd). If a newer Vero asks for approval even to complete, record it under ADR-003.
task: no JSON events: is --json in vero.task_args?Restore the default task_args.
task: no completion_resultThe agent ended without completing (guide §3.4 retry loop). If it repeats, raise it with the Vero owners.
task: slow: 104 s > 90 sVero answered, but slowly (degraded). Adjust task_slow only if the agreed threshold changes.
task: answered, but not with 'OK'A guardrail or the model answered differently. Vero is up (degraded).
chat: environment variable VERO_CHAT_TOKEN is not setRun setx (section 6), then sign out and in again.
chat: HTTP 401 (token rejected or expired)Renew the token.
chat: unreachable: CERTIFICATE_VERIFY_FAILEDSet chat.ca_bundle to the company CA file.
Status page "Reconnecting…"The page process stopped. Use the desktop shortcut after signing in again, or start_dashboard.bat.
"cannot listen on 127.0.0.1:8766"Change server.port, then run uninstall and install again.

14Update, migrate, remove

  • From 0.x (Vero Latency Monitor): run uninstall.bat in C:\Tools\vero-latency-monitor, otherwise both tools call Vero every 15 minutes. Its data stays there. V3 uses its own port (8766), task names and database, so the two can also run side by side.
  • Update V3: run uninstall.bat, replace the files (keep config\monitor.json and data\), then run setup.bat (Enter, Enter, … Y).
  • Remove: run uninstall.bat, then delete the folder. Nothing else is written to the system.

15Structure and quality

Domaindomain.pyPure rules (status, availability, incidents, timeline). No I/O, fully unit-tested.

Quality gates, all passing for 3.0.0:

  • ruff: lint, including the security (bandit) and bugbear rule sets, plus formatting.
  • mypy strict: type-checked for Linux, Windows and macOS.
  • 64 unit and integration tests on Python 3.8, 3.10, 3.11 and 3.13, clean with resource warnings treated as errors. The integration tests use a fake Vero CLI (all failure modes: down, auth, hang, no completion, refusal, slow) and a fake MCP server.
  • Real browser check with Playwright: the page renders and goes live, "Check now" works, there is no horizontal scroll at 390 px, and the console shows no errors.

Defects found and fixed during the 3.0 build:

  • subprocess pipes were not closed (a handle leak in the long-running page process);
  • "env": [] passed validation;
  • a POSIX-only call sat on a path the type checker could not prove was never taken on Windows;
  • the timeout grace period was too long for short timeouts;
  • the CLI being down would also have skipped the Chat check;
  • single slow answers flooded the incident list;
  • a favicon 404.
