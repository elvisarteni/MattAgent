Vero Latency Monitor: setup and user guide

A small standalone tool that measures how fast the Vero CLI answers. It sends the cheapest possible prompt on a timer, records every result and shows it on a live dashboard.

Tool version0.2.0
StoryASPF-1578: As a Quality Lead, I want to monitor latency in the VERO CLI responses.
Owner<< OWNER >> (Quality AI Automation, GenAI Group 3)
Governed bySCMP Quality AI Automation Platform (ASPF-1619): skeleton, naming, run manifest, peer review
Runs onWindows 10/11 laptop (also Linux and macOS), Python 3.8+, no internet, no admin rights, nothing to pip-install

1Overview

The Vero CLI is the client's AI command line tool. It gives access to several models behind pre-defined guardrails. The monitor treats Vero as a black box: it starts the CLI exactly as a user or an agentic workflow would, sends one tiny prompt and measures the time until the CLI finishes.

Acceptance criterionHow the tool meets it
Should execute the cheapest promptOne fixed prompt, Reply with OK, about 3 input tokens and 1 output token. You choose the cheapest model during setup. The prompt hash is recorded with every run.
Should support time trigger setupSetup installs a Windows Task Scheduler task (cron on Linux/macOS). It runs on battery, catches up after sleep, and never runs twice at once. As an alternative, the dashboard window can run the timer itself.
Record and dashboard dataEvery probe goes into a local SQLite database, and every run gets a JSON run manifest. The live dashboard starts at logon and has a desktop shortcut. You can export CSV or a self-contained HTML report.
Should be automatedAfter setup nothing needs a person: scheduled probes, the dashboard at logon, pruning of old data, rotating logs, and clean-up of stale locks.

2How it works

What one probe measures

FieldMeaning
total_msWall-clock time from starting the CLI process to its exit. This is the latency a user or workflow actually waits for, including CLI start-up, authentication, guardrails, the model call and output.
first_byte_msTime to the first non-empty output. The difference from total_ms shows how much time is spent after the answer starts (streaming, shutdown).
status ok exit code 0 and the answer contains the expect text
unexpected exit 0 but a different answer, for example a guardrail refusal
error non-zero exit code, or the CLI could not start
timeout no exit within timeout_s; the CLI and every process it started are killed
exit_code, out_chars, errorDiagnostics. The answer text itself is not stored; only its length, plus the first 300 characters of any error message.

Latency figures (p50, p95, max) use successful probes only. Availability counts every probe: ok / all × 100. On the dashboard a successful probe is shown as ok, slow (at or above warn) or very slow (at or above crit).

4Requirements

  • Python 3.8 or newer. Check with py --version. If it is missing, install it from Software Center, from python.org (tick Add python.exe to PATH), or with winget install Python.Python.3.12. No extra packages are needed.
  • Vero CLI installed and logged in for the same Windows user who will run the monitor. Try one call by hand first.
  • No admin rights, no internet access and no open ports: the dashboard listens on 127.0.0.1 only.
  • About 1 MB for the tool plus data. At a 15-minute interval with one model, 90 days of data is about 8,600 rows, under 2 MB.

5Install in 5 minutes

  1. Get the tool folder into a fixed, local folder such as C:\Tools\, which gives C:\Tools\vero-latency-monitor\. Avoid Downloads and OneDrive-synced folders, because the scheduled tasks point to this folder. There are three ways, depending on what your channel allows:
    • Git (recommended, SCMP): clone the repository from Bitbucket project QAI << repo URL >> into C:\Tools\vero-latency-monitor.
    • Single-file installer vero_latency_monitor_setup_0.2.0.py, for channels that do not accept archives. It is one plain-text Python file you can read before running. It recreates the folder and checks each file's SHA-256: 
      py vero_latency_monitor_setup_0.2.0.py C:\Tools
py vero_latency_monitor_setup_0.2.0.py --list      :: only show the contents
    • Rebuild document VeroLatencyMonitor_0.2.0_REBUILD.md, for channels that accept no archives and no scripts. It is one readable Markdown file with every source file as a code block, a SHA-256 list and instructions for an AI assistant. Give it to Vero CLI (or any AI coding assistant) with: "Follow the instructions at the top of VeroLatencyMonitor_0.2.0_REBUILD.md and rebuild the project in C:\Tools". The document includes a verify script that confirms every file is byte-identical. Put this guide in docs\ afterwards.
    • Zip vero-latency-monitor-0.2.0.zip, where archives are allowed: unzip to C:\Tools\.
    If your company blocks an attachment type, use an approved channel (Git, Teams or OneDrive link). Do not rename files to get past the filter.
  2. Optional: see the demo first. Double-click setup_demo.bat. It uses a bundled fake Vero CLI and seven days of sample data, and opens the dashboard. Demo data lives in data-demo\, apart from real data. Close the window to stop it.
  3. Double-click setup.bat. It walks you through everything:
    • asks for the Vero command, the model ids (cheapest first) and the timing, with sensible defaults (section 6);
    • runs doctor: one real test call per model, nothing stored, and a clear RESULT ready or NOT READY. If it is not ready, it offers to go through the questions again;
    • asks Install background monitoring? [Y/N]. On Y it installs the scheduled probe and a dashboard that starts hidden at every logon, puts a Vero Latency Dashboard shortcut on the desktop, and opens the dashboard.
  4. Done. Probes now run every N minutes with no one present. To look at the results, use the desktop shortcut or http://127.0.0.1:8765/.
Check it any time with status.bat: it shows the configuration, the last run, whether the dashboard is up, and the state of both scheduled tasks.

Linux and macOS use the same steps as commands: python3 vlm.py configure, python3 vlm.py doctor, python3 vlm.py install (cron) and python3 vlm.py open.

6Connect the Vero CLI

The monitor needs to start the Vero CLI once, non-interactively: pass the prompt, get the answer, exit. Find the right syntax with vero --help. setup.bat (or python vlm.py configure) asks for it as one line:

1. How to run the Vero CLI once, non-interactively. Check with: vero --help
   Placeholders: {prompt} = the probe prompt, {model} = model id. Without {prompt} the prompt goes to stdin.
   Command [vero -p {prompt} --model {model}]:
   found: C:\Users\me\AppData\Roaming\npm\vero.cmd

2. Model ids to probe, comma separated. Put the cheapest first. Empty = the CLI default model.
   Models []: small-model-id

3. Timing
   Probe every N minutes [15]:
   Timeout per call, seconds [60]:
   Warn from, seconds [5]:
   Critical from, seconds [15]:

saved C:\Tools\vero-latency-monitor\config\monitor.json
The exact Vero CLI flags are << to confirm with vero --help >>. Common patterns: vero -p {prompt} --model {model}, vero run --model {model} {prompt}, or vero chat --model {model} with the prompt on stdin (leave out {prompt}). If vero is not found, give the full path in quotes; where vero shows it.

Choose the cheapest model

  • List the models Vero offers (for example vero models, << confirm >>) and put the smallest or cheapest first.
  • To compare models, list more ids. Each run probes every listed model once, one after another, so the cost per run is one tiny prompt per model.
  • Leave the list empty to use the CLI's default model. The --model flag is then left out of the command.

Check the connection

python vlm.py doctor
config         C:\Tools\vero-latency-monitor\config\monitor.json
data           C:\Tools\vero-latency-monitor\data
executable     vero -> C:\Users\me\AppData\Roaming\npm\vero.cmd
cli version    vero 2.3.1
probe small-model-id ok          1843 ms   'OK'
               command: C:\...\vero.cmd -p "Reply with OK" --model small-model-id
RESULT         ready

If the status is unexpected, the CLI answered but the answer did not contain OK: it may print a banner first, or a guardrail may have rejected the prompt. Copy the command: line into a terminal to see the real output, then change expect in config\monitor.json (or set it to "" to accept any answer with exit code 0).

Editing the JSON by hand

Every setting is in config\monitor.json (section 10). Notepad is fine, including "UTF-8 with BOM". In JSON a Windows path needs doubled backslashes, "C:\\Tools\\vero.cmd", or forward slashes, "C:/Tools/vero.cmd". Run doctor after every edit; a mistake gives a clear config error message instead of a crash.

What install creates on Windows

Task Scheduler taskRunsSettings
VeroLatencyMonitorpythonw.exe vlm.py probe --trigger task --quiet every N minutesStarts on battery and keeps running if power is unplugged · runs a missed start after sleep · a new start is skipped while one is running · 1-hour limit · current user, no admin

The tasks are registered from XML, not with schtasks /TR. That is what makes the laptop settings above possible, and it avoids the 261-character command limit and quoting problems with paths that contain spaces. install also sets schedule.run_in_dashboard to false, so a dashboard opened by hand never probes twice. uninstall sets it back.

By default the tasks run only while the user is logged on, which suits a laptop. For a machine where nobody is logged on, open the task in taskschd.msc, choose Run whether user is logged on or not, and store the password. Some company policies block this; if so, use a functional account and record it in functional-accounts.md.

Probes older than retention_days (default 90) are deleted at the end of each run. Run manifests are small and are kept; delete old month folders under data\runs\ by hand if you need to.

12Security and guardrails

  • No secrets. The monitor never handles credentials; the Vero CLI uses its own login. cli.env is never shown on the dashboard or in reports, but it is plain text, so keep tokens out of it.
  • No content kept. Model answers are not stored, only their length. Error messages are cut to 300 characters.
  • Guardrail-friendly. The prompt is neutral and tiny. A guardrail refusal shows up as unexpected, which is itself a useful signal.
  • Local only. The dashboard binds to 127.0.0.1. It rejects requests addressed to any other host name, which blocks DNS rebinding, and it rejects "Run probe now" from other web pages, so a website cannot spend tokens. It has no login, so do not change server.host to 0.0.0.0 without approval and an authenticating reverse proxy.
  • Safe report. Data embedded in the HTML report is escaped, so a model label or error text cannot inject script.
  • Cost. One probe is a few tokens. One model every 15 minutes is 96 calls a day; three models every 5 minutes is 864. Keep the interval reasonable.
  • Git. data/, data-demo/, reports/, dist/ and config/monitor.json are ignored. Share configuration only through monitor.example.json.

13Troubleshooting

Start with status.bat and data\monitor.log: every run, error and crash is written there, even when the tool runs hidden.

SymptomCause and fix
"Python 3.8 or newer was not found"Install Python (section 4). If python opens the Microsoft Store, turn off the alias in Settings › Apps › App execution aliases; the batch files prefer py anyway.
config error: … invalid JSONA typo in monitor.json. The message gives the line and column. For paths use \\ or /. Or run setup.bat again.
doctor: executable NOT FOUNDVero is not on the PATH for this user. Give the full path (run where vero).
Every probe timeoutThe CLI waits for interactive input. Use its one-shot flag, or leave {prompt} out so the prompt goes to stdin. Raise the timeout if the model is simply slow.
Every probe unexpectedThe answer does not contain OK. Run the command: line from doctor by hand, then adjust expect.
error: exit 1, not logged in or unauthorisedLog in to Vero as the same Windows user the tasks run as.
Works by hand, fails from Task SchedulerDifferent PATH or user. Use the full path to Vero, then check "Last Result" in status.bat and data\monitor.log.
No new probes while on battery or after sleepTasks installed by 0.1.0 used the Windows defaults (AC power only). Run uninstall.bat, then setup.bat → Y.
Dashboard shows "Reconnecting…"The dashboard process stopped. Use the desktop shortcut after signing in again, or start_dashboard.bat. The data is safe.
"cannot listen on 127.0.0.1:8765"Another program uses the port. Set server.port (for example 8877), then reinstall so the shortcut uses the new port.
"Probing…" does not go awayA crashed run left a lock. It is ignored automatically after timeout_s × models + 120 s, and the next run removes it.
Twice as many probes as expectedTwo copies of the tool are installed in different folders. Run uninstall.bat in the old folder.

14Update and uninstall

Update:

  1. Run uninstall.bat.
  2. Unzip the new version over the same folder. config\monitor.json and data\ are not in the zip, so they stay.
  3. Run setup.bat. Press Enter to keep each value, then answer Y.

Old data stays readable, because the database schema is only created if it does not already exist.

Uninstall: run uninstall.bat, then delete the folder. Nothing else was written to the system: no registry entries, no installed packages, only the two tasks and the shortcut that uninstall removes.
