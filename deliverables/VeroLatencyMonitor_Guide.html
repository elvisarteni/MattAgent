Vero Latency Monitor: setup and user guide

A small standalone tool that measures how fast the Vero CLI answers. It sends the cheapest possible prompt on a timer, records every result and shows it on a live dashboard.

Tool version0.1.0
StoryASPF-1578: As a Quality Lead, I want to monitor latency in the VERO CLI responses.
Owner<< OWNER >> (Quality AI Automation, GenAI Group 3)
Governed bySCMP Quality AI Automation Platform (ASPF-1619): skeleton, naming, run manifest, peer review
Runs onWindows 10/11 laptop (also Linux and macOS), Python 3.8+, no internet, no admin rights

1Overview

The Vero CLI is the client's AI command line tool. It gives access to several models behind pre-defined guardrails. This monitor treats Vero as a black box: it starts the CLI exactly as a user or an agentic workflow would, sends one tiny prompt and measures the time until the CLI finishes.

Acceptance criterionHow the tool meets it
Should execute the cheapest promptOne fixed prompt, Reply with OK, about 3 input tokens and 1 output token. You choose the cheapest model once in the configuration. The prompt hash is recorded with every run.
Should support time trigger setupTwo options: the built-in scheduler while the dashboard runs, or Windows Task Scheduler (cron on Linux/macOS) installed with one command.
Record and dashboard dataEvery probe goes into a local SQLite database, and every run also gets a JSON run manifest. A live dashboard shows the results, and you can export CSV or a self-contained HTML report.
Should be automatedOnce the trigger is installed, runs need no one at the keyboard. Old data is pruned automatically and every run is logged.

2How it works

What one probe measures

FieldMeaning
total_msWall-clock time from starting the CLI process to its exit. This is the latency a user or workflow actually waits for, including CLI start-up, authentication, guardrails, the model call and output.
first_byte_msTime to the first non-empty output. The difference from total_ms shows how much time is spent after the answer starts (streaming, shutdown).
statusok exit code 0 and the answer contains the expect text · unexpected exit 0 but a different answer, for example a guardrail refusal · error non-zero exit code, or the CLI could not start · timeout no exit within timeout_s (the process tree is killed)
exit_code, out_chars, errorDiagnostics. The answer text itself is not stored; only its length, plus the first 300 characters of any error message.

Latency figures (p50, p95, max) use successful probes only. Availability counts every probe: ok / all × 100. On the dashboard a successful probe is shown as ok, slow (at or above warn) or very slow (at or above crit).

4Requirements

  • Python 3.8 or newer. Check with py --version or python --version. If it is missing, install it from Software Center or python.org and tick Add python.exe to PATH. No extra packages are needed.
  • Vero CLI installed and logged in for the same Windows user who runs the monitor. Test it once by hand in a terminal.
  • No admin rights, no internet access and no open ports: the dashboard listens on 127.0.0.1 only.
  • About 5 MB of disk plus data. At a 15-minute interval with one model, 90 days of data is about 8,600 rows, under 2 MB.

5Install

  1. Unzip vero-latency-monitor-0.1.0.zip to a fixed folder, for example C:\Tools\vero-latency-monitor. Do not run it from inside the zip or from the Downloads preview. The scheduled task points to this folder.
  2. Try the demo (optional, 1 minute). Double-click setup.bat with the demo argument, or run it from a terminal: 
    cd C:\Tools\vero-latency-monitor
setup.bat demo
start_dashboard.bat
    This uses a bundled fake Vero CLI (scripts\fake_vero.py) and seven days of sample data. When you are done, delete the data folder before connecting the real CLI.
  3. Real setup. Run setup.bat. It creates config\monitor.json and opens it in Notepad. Set the Vero command and the cheapest model (section 6), then save and close. Setup then runs doctor, which makes one test call without storing anything.
  4. Start the dashboard. Run start_dashboard.bat. The browser opens at http://127.0.0.1:8765/. Keep the window open; closing it stops the dashboard and its built-in scheduler.
  5. Make it unattended (recommended). Run install_schedule.bat, then set "run_in_dashboard": false in the config so runs are not duplicated. See section 7.

Linux and macOS: the same steps with python3 vlm.py init, python3 vlm.py doctor, python3 vlm.py serve --open and python3 vlm.py schedule install.

6Connect the Vero CLI

The monitor needs to start the Vero CLI once, non-interactively: pass the prompt, get the answer, exit. Find the right syntax with vero --help, then put it in cli.command as a list of arguments. {prompt} and {model} are filled in at run time.

The exact Vero CLI flags are << to confirm with vero --help >>. The examples below show the common patterns; adapt them.

Prompt as an argument (most CLIs)

"cli": {
  "command": ["vero", "-p", "{prompt}", "--model", "{model}"],
  "prompt_via": "arg",
  "timeout_s": 60,
  "version_command": ["vero", "--version"],
  "env": {}
}

Prompt through stdin

"command": ["vero", "run", "--model", "{model}"],
"prompt_via": "stdin"

Full path or wrapper script

"command": ["C:\\Users\\me\\AppData\\Roaming\\npm\\vero.cmd", "-p", "{prompt}", "--model", "{model}"]

In JSON, a backslash in a path is written twice. The monitor also resolves vero to vero.cmd or vero.exe on the PATH by itself.

Choose the cheapest model

  • List the models Vero offers (for example vero models, << confirm >>) and pick the smallest or cheapest one. Put its id in models.
  • To compare models, add more entries. Each run probes every listed model once, one after another, so the cost per run is one tiny prompt per model.
  • Use "id": "" to use the CLI's default model. The --model flag is then left out.
"models": [
  { "id": "small-model-id", "label": "cheap" },
  { "id": "",               "label": "default" }
]

The label is what the dashboard shows. Keep labels stable, because history is grouped by label.

Check the connection

python vlm.py doctor
config         C:\Tools\vero-latency-monitor\config\monitor.json
executable     vero -> C:\Users\me\AppData\Roaming\npm\vero.cmd
cli version    vero 2.3.1
probe cheap        ok             1843 ms   'OK'
               command: C:\...\vero.cmd -p Reply with OK --model small-model-id
RESULT         ready

If the status is unexpected, the CLI answered but the answer did not contain OK. The CLI may print a banner instead, or a guardrail may have rejected the prompt. Change expect to text the answer always contains, or set it to "" to accept any answer with exit code 0.

7Time trigger

Choose one of the options. If both are active, runs are still never parallel (a lock file prevents overlap), but you get twice as many probes.

A. Dashboard schedulerB. Windows Task Scheduler (recommended)
Runs whenThe dashboard window is openAlways while the user is logged on, even with no dashboard open
Set up"run_in_dashboard": true (default)install_schedule.bat, then "run_in_dashboard": false
Intervalschedule.interval_minutes (default 15), aligned to the clock: :00, :15, :30, :45

Windows Task Scheduler

install_schedule.bat            :: uses schedule.interval_minutes
install_schedule.bat --every 5  :: or a different interval

This creates the task VeroLatencyMonitor for the current user. The task runs pythonw.exe vlm.py probe --trigger task, so no console window pops up. Check it in taskschd.msc under Task Scheduler Library, or with:

python vlm.py schedule status

By default the task runs only while the user is logged on, which suits a laptop. To run it without anyone logged on, open the task in taskschd.msc, choose Run whether user is logged on or not, and store the password. Some company policies block this; if so, use a functional account and record it in functional-accounts.md.

Linux and macOS (cron)

python3 vlm.py schedule install     # adds one line marked "# vero-latency-monitor"
python3 vlm.py schedule remove

CSV columns

id, run_id, ts, epoch, model, model_id, status, total_ms, first_byte_ms, exit_code, out_chars, error. Timestamps are UTC (ISO 8601); the dashboard shows local time.

Retention

Probes older than retention_days (default 90) are deleted at the end of each run. Run manifests are small and are kept; delete old month folders under data\runs\ by hand if needed.

12Security and guardrails

  • No secrets. The monitor never handles credentials. The Vero CLI uses its own login. cli.env is not shown on the dashboard or in reports, but it is still plain text, so do not put tokens in it.
  • No content kept. Model answers are not stored; only their length is. Error messages are cut to 300 characters.
  • Guardrail-friendly. The prompt is neutral and tiny. A guardrail refusal shows up as unexpected, which is itself a useful signal.
  • Local only. The dashboard binds to 127.0.0.1 and has no login. Do not change server.host to 0.0.0.0 without approval and a reverse proxy with authentication.
  • Cost. One probe is a few tokens. With one model at 15 minutes that is 96 calls a day; with three models at 5 minutes it is 864. Keep the interval reasonable.
  • Git. data/, reports/ and config/monitor.json are ignored. Share configuration through monitor.example.json only.

13Troubleshooting

SymptomCause and fix
"Python 3.8 or newer was not found"Install Python and tick Add to PATH. If python opens the Microsoft Store, turn off the alias in Settings › Apps › App execution aliases, or use py.
doctor: executable NOT FOUNDVero is not on the PATH for this user. Put the full path in cli.command[0] (run where vero to find it).
Every probe timeoutThe CLI waits for interactive input. Use its one-shot flag, or switch to "prompt_via": "stdin". Raise timeout_s if the model is simply slow.
Every probe unexpectedThe answer does not contain OK. Run the command from doctor by hand to see the output, then adjust expect or the prompt.
error: exit 1, not logged in / unauthorisedLog in to Vero as the same Windows user the scheduled task runs as.
Works by hand, fails from Task SchedulerThe task runs with a different PATH or user. Use the full path to Vero in cli.command, and check data\monitor.log and "Last Result" in schedule status.
Dashboard shows "Server not reachable" or "Reconnecting…"The start_dashboard.bat window was closed. Start it again. The data is safe.
Port 8765 in useSet server.port or run python vlm.py serve --port 8877.
Twice as many probes as expectedBoth triggers are active. Set run_in_dashboard to false or remove the task.
"another run is in progress; skipped" in the logA run is still going. This is normal if a run lasts longer than the interval; otherwise a stale lock clears itself after timeout_s × models + 120 s.

14Update and uninstall

Update: run remove_schedule.bat, replace every folder except config\monitor.json and data\, then run install_schedule.bat again. The database schema is created if it does not exist, so old data stays readable.

Uninstall: run remove_schedule.bat and delete the folder. Nothing else is written to the system: no registry entries, no installed packages.
