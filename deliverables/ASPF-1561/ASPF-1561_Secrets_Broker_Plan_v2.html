ASPF-1561 Secrets Broker: how to do it

As a Platform Engineer, I want secure credential injection so that containers can access enterprise resources without exposing secrets.

Story · 3 SPBlocks ASPF-1563 Orchestrator SimulatorChild of DEART-544Objective ASPF-1679Assignee: Elvis-Nicolae Arteni

1. The idea in one picture

Do not build a vault. The broker is a thin step between an approved secret store (owned by IT) and the container runtime: at run start it fetches the secrets a run is allowed to use, hands them to the container as read-only files in memory, logs who used which secret, and removes everything when the run ends.

3. Design

Manifest: references, never values

Lives with the non-secret configuration (config/ in the repo, per the SCMP). Reviewed like code.

profile: orchestrator-sim
secrets:
  - name: bitbucket_token          # file /run/secrets/bitbucket_token
    ref: <store>/qai/bitbucket/qai-ci-readonly
    owner: functional              # functional | user
  - name: vero_aws_credentials
    ref: <store>/qai/vero/fn-qai-bedrock
    owner: functional
    target: /home/runner/.aws/credentials    # path to confirm with the Vero owners
    ttl: 1h                                  # short-lived role session

Command

qai-secrets run --profile orchestrator-sim --run-id "$RUN_ID" -- \
  docker run --rm qai/orchestrator-sim:1.4.0

The broker adds the mount (--mount type=bind,src=<tmpfs dir>,dst=/run/secrets,readonly), runs the container, masks known values in its output, scans the run folder, writes the access log and deletes the tmpfs folder, also on failure or Ctrl+C.

  • The tmpfs folder is created under $XDG_RUNTIME_DIR or /dev/shm (memory, never disk), mode 0700, one per run_id.
  • The bind source must be on the Docker host. If CI talks to a remote Docker daemon, the broker must run on that host (decide in phase 1).
  • Masking covers the plain value and its common encodings (base64, URL-encoded), because tools often print an encoded Authorization header.
  • If the runtime turns out to be Kubernetes, use the cluster's mechanism (External Secrets or the Secrets Store CSI driver) for steps 3–4; the manifest, logging, artifact guard and rotation parts stay the same.

Why files, not environment variables

  • Environment variables show in docker inspect, /proc/<pid>/environ, crash dumps and child processes, and are often printed by debug logging.
  • If a tool only reads an env var, the container entrypoint reads the file and sets it just for that process.

Where the code lives

orchestrator-code/src/orchestrator/adapters/secrets/: one adapter per store (the approved store, plus a local file adapter for tests only), the masker and the scanner in common/. Records in the platform docs: functional-accounts.md (secret location as reference, rotation, owner).

5. Tests

  • Canary: store a fake secret QAI-CANARY-<uuid>, run a container that prints it to stdout, writes it to a log and to an artifact. Expect: stdout masked, run fails at the scan, access log has the reference but not the value.
  • docker inspect of a running container shows no secret value.
  • Cleanup: kill the broker mid-run; the tmpfs folder is gone afterwards.
  • Rotation: change the secret in the store; the next run uses the new value without a rebuild.
  • Unit tests use the local file adapter and synthetic values only.
